## 2. NFC以外の販路の場合の「遊び方」設計

すでにシステム側に3つの入口が実装済みで、**新規の開発は不要**。どのURLを、
どのタイミングで、どこに載せるかという「運用」の話になる。

| 入口 | 使う場面 | 特徴 |
|---|---|---|
| `/t?u=00000000000000`（NFC・全枚共通） | キーホルダー本体を売る | 1枚1体。在庫は台帳では分からない |
| `/q/<コード>`（QR・1枚ずつ発行） | キーホルダー以外の「モノ」に紐づける | 管理画面「依代の発行」で1件ずつ発行。配布元の記録が残る |
| `/w`（Web単独、モノ不要） | モノを介さず今すぐ始めてもらう | `ENTRY_OPEN:1` を立てている間だけ有効 |

### 2-1. チャネル別の当てはめ方

- **通販の同梱物・パッケージ挿入カード**：カードに `/q/<コード>` のQRを1枚ずつ印刷。
  「依代の発行」で必要枚数分のコードを事前に発行しておき、印刷会社にはQR画像だけ渡す
  （キーホルダーと同じ扱いなので、UIDの問題は発生しない）。
- **店頭・委託販売（雑貨店等）**：同上。棚に並べる分だけコードを発行し、
  什器のPOPにQRを載せる。台帳に配布元（どの店に何枚渡したか）をメモしておけば、
  在庫と実売のズレがあった時に追える。
- **イベント配布・ノベルティ**：数量が読める場合は `/q/<コード>` を刷ったカードを配る。
  数量が読めない・その場でURLを口頭案内したい場合は `/w` を大きめのQRやリンクで掲示。
  ただし `/w` は「依代を持っていない人向けの入口」なので、
  **デプロイ時に `ENTRY_OPEN:1` を立てる必要がある**（`npx wrangler deploy --env="" --var ENTRY_OPEN:1`。
  イベント終了後は必ず外す＝通常デプロイに戻す）。
- **デジタル限定配布（SNS投稿・note記事・メルマガのリンクなど、モノを一切介さない体験）**：
  `/w` のリンクをそのまま貼る。開いた瞬間に1体生まれ、同じ端末で開き直しても増えない。
  台帳には残らないので「どれだけバズったか」は集計上 `web` カウントとして見える
  （`direct` ＝画面のボタンから作った人とは別集計）。
- **法人・コラボ限定の姿（期間・場所限定のキャラクター性格や見た目を出したい場合）**：
  これは `/q/<コード>` 側でしか成立しない（`/t` の共通URL方式では「限定の姿」は使えない、
  と `docs/OPERATIONS.md` に明記あり）。コラボ企画は必ずQR／個別コード方式で。

### 2-2. 運用上の注意点（既存ドキュメントより）

- 依代（キーホルダーやコード）を持たない人からの新規作成は、**既定では閉じている**
  （`ENTRY_OPEN` が立っていない限り `/w` と `/add` の3番ボタンは使えない）。
  非NFC販路を「常設」で回す場合は `ENTRY_OPEN:1` を常時立てる運用になるが、
  その場合は1日あたりの新規作成上限が「誰でも入れる状態：1回線あたり3体／日」に
  下がる点に注意（依代を経由すれば10体／日、管理者は無制限）。
  イベントなど短期の非NFC施策は「その期間だけ `ENTRY_OPEN:1` で出して、終わったら戻す」
  運用が安全。
- QR方式は在庫（未使用コード数）と配布元がシステム側の記録に残るが、
  `/w` は残らない。**在庫管理や配布実績を追いたい販路は必ずQR（個別コード）方式にする。**

## 3. NFCキーホルダーのエンコードで「UIDが無理」と言われた場合

### 3-1. まず何が起きているかの整理

このシステムは、タグ全部に**まったく同じURL**
（`https://app.waketama.com/t?u=00000000000000`）を書き込み、
NTAG213/215/216 が持つ**「UID ASCIIミラー」**という機能で、読み取り時に
チップ固有のUID（工場出荷時に焼かれた書き換え不能な番号）をURLの `0` の部分に
自動で差し込ませることで「1枚1体」を成立させている。

業者が「UIDは無理」と言うとき、実際に無理なのはほぼ確実に
**この“UID ASCIIミラー設定”という特殊な書き込みオプション**の方であって、
「UIDという概念自体を扱えない」わけではない。量産系の書き込み業者は
定型のNDEF（URLやテキスト）を大量に書くことはできても、
UIDミラーの位置合わせ・有効化までは対応していないところが多い
（対応チップ自体は一般的でも、書き込み機のソフト側の対応が分かれる）。

### 3-2. すでに用意されているフォールバック：1枚ずつコードを振る方式

このシステムは最初から、QRコードと同じ方式（**1枚ずつ別のURLを書く**）を
NFCタグに使うことも想定して作られている。UIDミラーが使えなくても、
サービスとしては何も困らない。

管理画面の「依代の発行」で必要枚数分のコード（`/q/<コード>` 形式のURL）を発行し、
そのURLをそのまま1枚ずつタグに書き込めばよい。

| | 共通URL（UIDミラー） | 1枚ずつコード |
|---|---|---|
| 書き込み | 全枚同じ内容。外注しやすい | 1枚ずつ内容が違う |
| 未使用在庫 | システム側では分からない | 分かる |
| 配布元の記録 | 残らない | 残る |
| 限定の姿（期間・コラボ限定演出） | 使えない | 使える |

むしろ「配布元が分かる」「限定演出が使える」という点では、
1枚ずつコード方式の方が優れている面もある。UIDミラーは
「外注コストを下げるための省力化」であって、必須の技術ではない。

### 3-3. 具体的な対応の選択肢

1. **業者への発注内容を変える（同じ業者のまま解決できる可能性）**
   「UIDミラー」ではなく、**「1枚ずつ異なるURL（NDEF）を書き込む個別シリアル書き込み」**
   を依頼する。これは一般的な会員証・スタンプラリー用ICタグの発注でもよくある
   仕様のため、対応できる業者の母数はUIDミラーよりかなり多い。
   発注時に渡すのは「URLのテンプレート＋連番」ではなく、
   **わけたま側で発行済みの完成した `/q/<コード>` のURL一覧そのもの**
   （順不同でよい。1枚に1URLが対応していればよく、印刷会社の管理番号と紐付ける
   必要もない）。

2. **UIDミラー対応を明言している別の業者を探す**
   どうしても共通URL方式（外注コストを最小化したい・将来的に数千枚単位で
   増産したい）を続けたい場合は、発注時に次の文言をそのまま伝えて対応可否を
   確認する（`docs/OPERATIONS.md` に記載の実際の発注文言）：

   > チップ: NTAG213 / 215 / 216（UIDミラー対応のもの）
   > 書き込む内容: 指定のURL（全枚共通）
   > UID ASCIIミラーを有効化し、ミラー位置をURLの `0` が14個並ぶ先頭に合わせる
   > カウンタミラーは任意

   この文言に対して「UIDミラーの意味が分かった上で」対応可否を答えられる業者は、
   実際に対応できる可能性が高い。

3. **自分（少量なら）で書き込む**
   数十〜百枚程度であれば、外注せず自前で書き込む方が早いことも多い。
   - スマホ用アプリ（iOS/Androidとも対応）：**NFC Tools / NFC Tools Pro** など、
     NDEFのURLを1件ずつ書き込めるアプリで、依代の発行で出した
     `/q/<コード>` のURLを1枚ずつ書けばよい
   - 量が読める場合は、数千円台のUSB接続NFCリーダー/ライター
     （ACR122U等）＋PC用ツールで、URLリストを流し込みながら連続書き込みする
     運用も可能
   - どちらの方法でも「1枚ずつ違うURL」を書く方式なのでUIDミラーの知識は不要

### 3-4. どちらの方式でも共通の注意

納品・書き込み後は**必ず2枚以上かざして、別々のキャラクターが出ることを確認する**。
（UIDミラー方式で設定を忘れて出荷されると、全部のタグが同じ人格を指してしまう。
1枚ずつコード方式でも、同じコードを誤って2枚に書いてしまうミスは起こり得るので、
確認の手間は同じようにかけること。）
