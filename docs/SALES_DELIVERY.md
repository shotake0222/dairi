# 販売時に何を納品するか

最終更新: 2026-09-19

---

## 0. まず結論

**売るのは分身そのものではない。** 売るのは次の2つ。

1. **その人格を、相手の環境で動かせる形にした写し**
2. **その写しを取り出す権利（引換券）**

分身の所有権は、育てた本人のまま動かない。こちらが渡すのは写しと、期限つきの鍵。
この切り分けをしておかないと、「売ったあとに本人が削除したらどうなるのか」
「買い手が勝手に育てられるのか」に答えられなくなる。答えは、どちらも起きない。

| よくある質問 | 答え |
|---|---|
| 買い手は分身を書き換えられる？ | できない。渡す口はすべて読み取り専用 |
| 買い手と話すと、持ち主の分身が育つ？ | 育たない。MCPの応答は何も保存しない経路を通る |
| 本人が削除したら、納品済みの写しは？ | 手元の写しは残る。引換券からの取り出しはできなくなる |
| 更新は届く？ | MCPなら都度取りに来るので届く。ファイル納品は届かない（再発行が要る） |

## 1. 商品は4つ

定義は `src/delivery.ts` の `SKUS` が唯一の定義元。管理画面の「納品」タブは、その配列を表示しているだけ。
**この文書と実装がずれたら、実装が正しい。**

### 1-1. 人格カード（`card`）

**買い手**: 自前のLLM基盤を持っていて、その上でこの人格を動かしたい相手。

渡すもの:

| ファイル | 中身 |
|---|---|
| `persona_card.json` | 性格6軸・価値観・口調・覚え書き・会話の例・身体のパラメータ |
| `system_prompt.txt` | そのままモデルに渡せる形 |
| `Modelfile` | Ollama用（ローカルで動かす場合） |
| `README.md` | 載せ方と、**含まれていないもの**の説明 |

含まれないもの: 会話の全文ログ、持ち主の連絡先、年収などの機微な属性。

### 1-2. 振る舞いプロファイル（`behavior`）

**買い手**: AIを積んでいない機器を作っている相手（ロボット・玩具・サイネージ・アバター）。

ここが他社と一番違うところ。**言語モデルが要らない。**
「人格 → 振る舞い」の翻訳はこちらのサーバ（`src/persona/avatarProfile.ts`）で済ませてあるので、
渡すのは**数値と識別子だけの数百バイト**（実測で1体あたり約250バイト）。ESP32やRaspberry Pi Picoでも動く。

実際の書き出し（`npm run persona:fixtures` で作った検査用の1体。256バイト）:

```json
{"v":1,"id":"5b0a7533","n":"さきがけ","m":[77,73,85,458,1212,65],
 "p":[1.3,0.7],"e":[65,17],"t":[55,88,74,26,84,66],
 "c":["prefer_novel_options","offer_choices_not_answers","track_progress",
      "prioritize_enjoyment","tolerate_open_plans","take_initiative"]}
```

会話・覚え書き・属性は**1文字も含まない**。これは方針ではなく、
渡す直前に機械で検査していて（`auditCompact`）、落ちたものは配信しない。
部屋に置く機器や人に配るデバイスに、その人の生活が焼かれることは起こらない。

参照実装も一緒に渡す（Python / Arduino / MicroPython）。検証手順は
[EDGE_DEVICE_TEST.md](EDGE_DEVICE_TEST.md)、
**「文字の会話が、どうやってこの数値になるのか」は [TEXT_TO_BEHAVIOR.md](TEXT_TO_BEHAVIOR.md)。**

### 1-3. MCP接続（`mcp`）

**買い手**: 自社のAIエージェントから、この人格を参照したい相手。

ファイルを渡すとその瞬間の写しで止まるが、MCPなら相手のエージェントが必要なときに取りに来る。
**相手がAIのときの納品形はこれ。**

| 道具 | 返すもの |
|---|---|
| `persona_profile` | 人物像（性格・価値観・口調・身体のパラメータ） |
| `persona_behavior` | 振る舞いプロファイルと同じ数値 |
| `persona_reply` | この人格として1回答える。**分身側には何も保存しない** |

書き込みの道具は用意していない。買い手が持ち主の分身を書き換えられる設計にはしない。

### 1-4. 自分専用のSLM一式（`slm`）

**買い手**: クラウドに繋がず、手元の小さなモデルでこの人格を喋らせたい相手。

| ファイル | 中身 |
|---|---|
| `Modelfile` | 土台のSLM＋人格。`ollama create` だけで動く |
| `train.jsonl` / `eval.jsonl` | 口調をさらに寄せたいとき用のLoRA学習データ |
| `README.md` | 0.5B〜8Bの選び方、学習手順、移ったかどうかの確かめ方 |

> **用語**: SLM は Small Language Model。**SML は Standard ML という別の言語名**なので、
> 資料でも口頭でも SLM と言うこと。

学習データが少ない分身では `stats.enough` が false で返る。
**その状態で学習すると、口調が移るより先に過学習する。** 黙って渡さず、会話を重ねてから出し直す。

### 1-5. 判断プロファイル（`decision`）

**買い手**: Jev のような「文章を書かない判断特化モデル」に、**誰の判断か**を与えたい相手。

Choice / Score / Noul の問いと、この人の既定の答え（`prior`）、その根拠（`because`）、
そして全体の確からしさ（`confidence`）を返します。

> **Jev そのものは作れません。** TypeSafe AI の製品で、重みもファインチューンの口も非公開です。
> こちらが渡すのは、判断特化モデルへ流し込む「この人の判断の癖」まで。
> ここを「自分専用のJevが作れます」と言うと、実物が出せずに商談が壊れます。

判断特化モデルは速くて安いが、**誰の判断なのかは持っていない**。そこを埋めるのがこの商品です。

### 1-6. 持ち出し一式（`bundle`）

**買い手**: ネットに繋がない環境（工場・車内・展示会場・医療機器まわり）。

1-1 と 1-2 を1つのJSONにまとめたもの。`files` の各キーがそのままファイル名になる。
受け取り側は `jq` か数行のスクリプトで展開できる。

納品後の更新は届かない。更新が要る取引なら、期限を短くして再発行する運用にする。

## 2. 相手によってどれを売るか

```
相手はAIを持っている？
├─ はい → 何に使う？
│         ├─ 自社エージェントから参照        → MCP接続
│         ├─ 自前のモデルに焼く               → 人格カード
│         ├─ 手元の小さなモデルで喋らせる     → 自分専用のSLM一式
│         └─ 判断特化モデル（Jev等）に流し込む → 判断プロファイル
└─ いいえ → ネットに繋がる？
            ├─ はい  → 振る舞いプロファイル
            └─ いいえ → 持ち出し一式
```

迷ったら **人格カード＋振る舞いプロファイル**の2点にしておくと、
相手の技術選定が変わっても作り直しにならない。

## 3. 納品の手順

### 3-1. 事前に確認すること

- [ ] **持ち主の同意**があるか（はじめる前の同意＝`terms`、統計利用なら `aggregate`）
- [ ] 人格の**厚み**が売れる水準か（管理画面の「人格データ」タブ。60点以上が目安）
- [ ] 相手の環境（LLMの有無、ネットの有無、機器の種類）を聞き取ったか
- [ ] 期限を決めたか（既定90日。無期限にしない。失効させ忘れが必ず起きる）

### 3-2. 引換券を発行する

管理画面 →「納品」タブ → 分身のID・渡し先・日数・範囲を入れて発行。

**平文が出るのは発行の1回だけ。** 保存しているのはハッシュなので、こちらでも後から見られない。
控え忘れたら失効させて出し直す。

発行すると、そのまま先方に送れる手順が画面に出る。

### 3-3. 先方が取り出す

```bash
# 人格カード
curl -o persona_card.json "https://app.waketama.com/api/delivery?scope=card&token=<引換券>"
curl -o Modelfile          "https://app.waketama.com/api/delivery?scope=card&format=modelfile&token=<引換券>"

# 振る舞いプロファイル（LLM不要）
curl -o persona.min.json   "https://app.waketama.com/api/delivery?scope=behavior&token=<引換券>"

# 持ち出し一式
curl -o bundle.json        "https://app.waketama.com/api/delivery?scope=bundle&token=<引換券>"
```

MCPの場合:

```
エンドポイント: https://app.waketama.com/mcp
認証:          Authorization: Bearer <引換券>
```

### 3-4. 納品後に見ること

管理画面の引換券一覧に**使用回数**が出る。
**「未使用」のまま数日経っている先は、たいてい繋ぎ方で詰まっている。** こちらから連絡する。

## 4. 価格の考え方（叩き台。確定ではない）

値付けの根拠になるのは「相手が自前でやると何が要るか」。

| 商品 | 相手が自前でやる場合に必要なもの |
|---|---|
| 人格カード | 対象者への聞き取り、設計、プロンプトの作り込み（数十時間） |
| 振る舞いプロファイル | 性格 → 動きの対応づけの設計と実装、実機での調整 |
| MCP接続 | 上に加えて、参照の仕組みの運用 |
| 持ち出し一式 | 上に加えて、オフラインでの検証環境 |

1体あたりの単価より、**用途と期間で分ける**ほうが説明しやすい。

- 検証用（90日・1体・更新なし）
- 製品組み込み（1年・N体・更新あり＝MCP）
- 匿名集約のみ（個人の人格は渡さず、セグメント統計だけ。`/api/market/insights`）

匿名集約は別物として扱うこと。あれは個人の人格ではなく、
k-匿名（最小コホート20）を満たした統計で、同意の範囲も別になっている。

---

## 5. 断るべき取引

- **持ち主の同意（`terms`）が取れていない**分身の納品
- 買い手が**本人の特定**を目的にしている（属性の逆引き、名寄せ）
- 納品物を**第三者へ再販**する前提の取引（引換券の又貸しを含む）
- 実在の人物を模した分身を、**本人の同意なく**作らせて売ること

いずれも、いったん通すと後から戻せない。
