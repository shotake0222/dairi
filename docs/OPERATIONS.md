## 0. このサービスは何を預かっているか

運用の判断はすべてここから出てくる。

- **利用者は会員登録をしていない。** 持ち主かどうかは、その端末のブラウザに入っている印だけで決まる
- **運営は会話の中身を読まない。** 復旧の本人確認も、名前・見た目・育ち具合といった中身以外で行う
- **消したら戻らない。** バックアップから個人の分身を復元する仕組みは持っていない

つまり、**こちらの操作ミスが、利用者にとっては「育てた分身が消えた」になる**。
迷ったら、消さない・止めない方へ倒すこと。

## 1. 毎日（5分）

管理画面（`/admin?key=<合言葉>`）の「概況」を開いて、次の4つだけ見る。

| 見るもの | 正常 | おかしいときの動き |
|---|---|---|
| 分身の総数 | 前日から増えている | 増えていない → 依代が配れていないか、入口が壊れている（§6-1） |
| 日次の `tap` / `scan` | 配った数と釣り合う | `tap` だけ0 → NFCの書き込み内容を疑う |
| `chat` の数 | 分身の数に対して極端に少なくない | 少ない → 生まれた直後に離脱している（§6-2） |
| 問い合わせ・購入希望 | 未対応が溜まっていない | 溜まっている → その日のうちに返す |
| タブの赤い数字（広告・ランドマークの申込／Web申し込み） | 0 | 1以上 → §2-3-2。**自動では掲載・承認されない**ので、放っておくと相手が待ち続ける |

`/api/health` も開く。**`ok: false` が出ていたら、その日はそこから**。

## 2. 毎週（30分）

### 2-1. 依代の在庫

「依代（タグ・QR）」タブ。

- **未使用が残り少ない**（目安: 発行数の2割を切った）→ 追加発行して書き込み・印刷を手配する
- **配布元ごとの使用済み数**を確認。設置先に報告する数字はここ
- **配ったのに1枚も使われていない配布元** → 置き場所が見えていない可能性が高い。先方に確認する

### 2-2. 納品の後追い

「納品」タブの引換券一覧。

- **「未使用」のまま数日経っている先** → ほぼ確実に繋ぎ方で詰まっている。こちらから連絡する
- **期限が2週間以内に切れる券** → 継続するか確認する。切れてから言われると印象が悪い
- **身に覚えのない「失効」が付いた券** → 持ち主が「法人へ渡すことを許可する」を外した（§4-7）。
  **券を出し直さないこと**（出そうとしても 409 で止まる）。先方には「提供元の都合で終了した」とだけ伝え、
  誰がなぜ外したかは伝えない。月額の取引なら、代わりの分身を提案する

券を出す前に、その分身の持ち主が許可を入れているかは、発行ボタンを押せば分かる
（入っていなければ「この分身の持ち主は、法人への個別提供を許可していません」で止まる）。
**持ち主に許可を入れてもらうよう、運営から働きかけることはしない**（連絡先も持っていない）。
料金は `/biz` の料金節が唯一の定義元。見積もりはそこから出す。

### 2-3. メタバースのエリアとミニゲーム

管理画面「メタバース管理」「ミニゲーム管理」タブ。

- **期間の終わった広告・キャンペーンの看板を下げる**（置いたままにすると、終わった企画のクーポン案内が出続ける）。
  キャンペーンのエリアは、作るときに**終了日時**を入れておけば自動で閉じる
- 状態の列を見る。「近日開放」の日時が合っているか、終わったはずのエリアが「公開中」のままになっていないか
- 看板の画像・動画が出ているか、「開く」で1度見る（相手のサーバーの設定変更で、ある日突然出なくなる。CORS）
- 満員の報告が続くエリアは、「複製」で同じエリアをもう1つ作って分ける（1エリア12端末まで）
- ミニゲームで不具合の報告があったら、直るまで「ミニゲーム管理」で**止める**（置いた設定は残る。戻せばまた出る）

### 2-3-2. 申込・申し込みの確認（広告・ランドマーク／Web申し込み）

管理画面のタブに赤い数字が出たら、確認待ちがある。

- 「広告・ランドマーク」→「申込」: 中身（文字・画像・リンク・クーポン）を確かめて**承認**（金額・決済リンク）か**見送る**。
  入金を確かめたら**支払い済み**（その日から掲載）。**自動では掲載されない**ので、放っておくと申込者が待ち続ける
- 承認・見送りの連絡は自動では届かない。申込者の連絡先へ知らせる（申込者の状況ページにも出る）
- 「広告・クーポン」: 期限の過ぎたクーポンを出し続けていないか、回数（詳細・リンク・クーポン）を広告主へ報告するならここ
- 「招待・申し込み」: Web申し込みを承認すると、申込者の状況ページに「分身をはじめる」が出る。連絡先へリンクを知らせてもよい

### 2-3-3. 通貨・お店（管理画面「通貨・お店」）

- **集計**: 「直近30日の出入り」で、クリア・おしゃべりの回数が急に増えていないか。1体だけ極端なら「付与・回収と、財布の確認」で出入りを見る
  （クリアの判定は端末なので、ずるはできる。1日の上限で止まるが、続くなら回収して理由を残す）
- **在庫**: 在庫のある商品（限定品・引換券）が売り切れていないか。売り切れのまま置くと「売り切れ」ばかりのお店になる
- **引換券**: 提携店ごとの「未使用」「使用済み」。期限切れが多い提携店は、特典か期限を見直す
- 提携店から「暗証番号をなくした」→ 「提携店」の「暗証番号を作り直す」。**新しい番号は1回しか表示されない**ので、その場で安全な方法で伝える
  （メール・チャットに平文で残さない。電話か手渡しが基本）

### 2-4. 設問の効き具合

「設問」タブと「人格データ」タブ。

- 厚みの平均が上がっているか。上がっていないなら、設問が答えにくい可能性がある
- 特定の設問だけ「あとで」が多い → 文面を直す（デプロイ不要でその場で反映される）

## 4. よくある依頼への対応

### 4-1. 「分身が消えた／操作できなくなった」

**まず伝えること: データは消えていない。** 「この端末が持ち主だと確認できない」だけの状態。

1. **引き継ぎコードを持っていないか聞く。** 持っていれば、チャット画面の「📦 保存/復元」で本人が即座に戻せる。ここで終わることが多い
2. 無ければ `/recover` のフォームから送ってもらう
3. 管理画面「分身の復旧」で、依代のID か 分身のID を引く
4. 出てくる情報（名前・見た目・育ち具合・誕生日・覚え書きの件数）で**本人確認の質問をする**
   - 「この子の名前は？」「いつごろ育てはじめましたか？」「どんな見た目でしたか？」
   - **会話の中身は聞かない。こちらにも見えていないし、聞けば見ていると思われる**
5. 確認できたら引き継ぎコードを発行して伝える

> **所有権を動かす操作。** 別人に渡すと、その人の分身が他人のものになる。
> 迷ったら発行しない。もう一度質問する方がはるかに安全。

### 4-2. 「削除してほしい」

本人が画面から消せる（チャット画面 → 設定 → 削除）。案内するだけでよい。
**運営側から消さない。** 取り違えたときに戻せない。

消えるもの: 性格・記憶・覚え書き・答えた属性・集計用の記録・出品・出会いの履歴・
公開ディレクトリへの掲載・依代との対応・生まれた入口の記録。

### 4-3. 「同じ依代で、もう1体育てたい」

できない（1つの依代につき1体）。既存の子を削除すれば、その依代は次にかざしたときに新しい子を生む。
**削除すると前の子は戻らない**ことを必ず先に伝えること。

別の子が欲しいなら、別の依代を使うか、`/add` から端末だけで始められる。

### 4-4. 「機種を変える」

事前なら: チャット画面の「📦 保存/復元」で引き継ぎコードを出しておいてもらう。
事後なら: §4-1 の復旧。

### 4-5. 「文字で話しているだけなのに、ロボットが動くの？」

商談でも利用者からも、いちばん多い質問。**毎回LLMに考えさせているわけではない**と伝えること。

1. 会話から性格6軸と価値観8軸を取り出す
2. それを「動きの大きさ・返すまでの間・対人距離」など**9項目の数値**へ翻訳する
3. 機器はその数値を読んで動く。**この段階にLLMは要らない**

実測の例（性格が逆の2体・同じファーム）: 返すまでの間 458ms / 890ms、身振り 2回 / 1回。
**この数字は測り直すたびに少し動く**（2体はその場で作り直しており、性格の抽出をAIが行うため）。
差の向きは変わらないので、値そのものではなく「速い子と遅い子が出る」と伝えること。
詳しくは [TEXT_TO_BEHAVIOR.md](TEXT_TO_BEHAVIOR.md)。**限界（言葉しか観測していないこと、
対応づけが初期値であること）も一緒に伝える**——伏せると、実機で差が小さかったときに仕組みごと疑われる。

### 4-6. 「子どもが使っている」

保護者の同意のもとで使ってもらう前提。心配の内容によって:

- 会話の中身 → 運営は読まない。本人は `/profile` で「覚えていること」を全部見られるし、直せる
- 属性 → すべて任意。同意をオフにすれば、答えた内容もその場で消える
- やめたい → 削除すれば全部消える
- 法人へ渡らないか → 「法人へ渡すことを許可する」は、はじめるときの同意に含まれる（同意の画面に全部書いてある）。
  心配なら「🪪 あなたのこと」で**オフにすれば、1体の写しは誰にも渡らない**（オフにした時点で、発行済みの受け取りの権利も失効）
- メタバース → 見知らぬ人と自由な文字のやりとりはできない（見えるのは分身の名前・姿・動きと、分身の言葉だけ）。
  通貨はお金で買えないので、子どもが課金してしまうことはない

### 4-7. 「自分の分身が、企業に渡っていないか心配」

`/profile`（チャット画面の「🪪 あなたのこと」）の一番下を見てもらう。

- 「この分身の写しを、法人へ渡すことを許可する」が**オフなら、1体の写しは誰にも渡っていない**
  （2026-09-24 の同意の版5から、はじめるときの同意に含めている。**既定はオン**なので、渡したくない人にはオフにしてもらう）
- オンなら、その下に「いまこの子の写しを受け取れる法人: N件」が出ている
- **オフにすれば、その場で全部失効する。** 運営の作業は要らない
- 渡る範囲: 性格・口調・声・価値観の傾向・身体の動かし方の数値と、選択肢で答えた属性（年収を除く）、分身の名前。
  **会話の本文・覚え書き・記憶・年収・入力方法の設定・分身の識別子は、オンでも渡らない**
- 相手がすでに手元に取り出したファイルは、こちらからは消せない。そこは正直に伝える

統計（「統計として使うことを許可する」）は別物。あちらは個人が特定されない集計で、1体の写しではない。

### 4-8. 商談で「会話のデータも欲しい」「学習データ付きのSLMが欲しい」と言われた

**他の方が育てた分身では出せない**（規約で約束している。実装でも出ない）。代わりに:

- 御社の担当者が**自分で分身を育てれば**、その分身の人格カード（覚え書き・応答例入り）と
  学習データ付きのSLM一式を、本人として無料で書き出せる（チャット画面の書き出し、`format=slm`）
- 他の方の分身から渡せるのは、性格・口調・価値観・身体の数値まで。人格は載るが、口調の手本（応答例）は付かない

「他の人の分身の会話を、特別に出してほしい」は断る。例外を作れる仕組み自体を持っていない。

### 4-9. 「同意の画面が、開くたびに出る」

- 同意の文面の版が上がった直後（2026-09-24 に版5へ上げた）は、**分身ごとに1回だけ**出る。それは正常
- 2回目以降も出るなら: その端末に持ち主の印が無い・古い（別の端末で育てた子）→ §4-1。
  「同意してはじめる」を押してもエラーになる → 電波の悪い場所。押せた後は、その端末では同じ版の間は出ない（端末に「同意済み」の印を残している）
- メタバースの入口の「気をつけること」の説明は、はじめての1回だけ開いて見せ、2回目からは畳んである（見出しを押せば読める）

### 4-10. 「メタバースのお店が開かない」「コインが貯まらない」「引換券が使えない」

| 言われたこと | 確かめること |
|---|---|
| お店が開かない | HUD の「🛍 お店」から開けるか（屋台は縦長の画面だと端に隠れる）。「いまはお店・財布を開けませんでした」なら **migration 0015 が本番に当たっていない**（§7） |
| 「この端末で育てている子を選ぶと…」と出る | 連れて入った子に、この端末の持ち主の印が無い（別の端末の子）。§4-1 |
| コインが貯まらない | 1日の上限（既定150）に達した／同じ屋台は1日1回／試し場では貯まらない／「通貨とお店を使う」がオフ。財布の「出入り」で最後に貯まった時刻を見てもらう |
| 「引き換えは準備中です」 | 「提携店の引換券への引き換えを受け付ける」がオフ。提携店と特典が決まってからオンにする |
| 店頭で「見つからない」 | 番号の打ち間違い（O と 0、I と 1 は使っていない）か、**別の店の暗証番号**。同じ店の番号で試してもらう |
| 店頭で「使用済み」 | すでに使われた券。取り消し・再発行はしない（二重に使える穴になる）。お客さま都合なら、提携店と相談のうえ運営からコインを付与して買い直してもらう |
| 「今日はこれ以上確かめられません」 | その回線で間違いが30回を超えた。翌日に戻る。店頭の端末で続くなら、暗証番号を作り直して伝え直す |
| 「コインを現金にしたい」「友だちにあげたい」 | できない（規約10-5）。お金で売らない・戻さない・渡さないのが、法律上この形でいられる前提 |

## 5. 依代を配るとき

### 5-0. タグに書き込むURLは、これ1本（全枚同じでよい）

```
https://app.waketama.com/t?u=00000000000000    ← NFCタグ。**全部これを書き込む**
https://app.waketama.com/q/<コード>             ← QRは1枚ずつ違うコード
```

**1枚ずつ違うURLを用意する必要はない。** ここが成立しないと、数百枚を外注して売ることができない。

#### なぜ同じURLで「1枚1体」になるのか

NTAG213/215/216 には **UIDミラー**という仕組みがある。
読み取られた瞬間に、**チップが自分の固有番号（UID・14文字）を、URLの中の `0` の並びに
差し替えて**返す。

```
書き込む内容 : https://app.waketama.com/t?u=00000000000000   （全枚同じ）
1枚目が返す  : https://app.waketama.com/t?u=04a1b2c3d4e5f6
2枚目が返す  : https://app.waketama.com/t?u=0499aa11bb22cc
```

UIDは工場で焼かれていて書き換えられないので、**こちらで番号を振る必要がない**。
NDEFの中身として読まれるため、iPhoneでもAndroidでも同じように効く
（Web NFC のようにブラウザの対応に左右されない）。

#### タグ屋さんへの発注内容（そのまま伝える）

- チップ: **NTAG213 / 215 / 216**（UIDミラー対応のもの）
- 書き込む内容: 上のURL（全枚共通）
- **UID ASCIIミラーを有効化**し、ミラー位置をURLの `0` が14個並ぶ先頭に合わせる
- カウンタミラーは任意（有効でも動く。区切りの `x` より後ろは読み捨てている）

#### 納品されたら、必ず2枚かざす

> **いちばん怖い失敗は、ミラーの設定を忘れて出荷すること。**
> そのとき全部のタグが `0` のままのURLを返すので、本来なら
> **買った人全員が同じ分身を共有する**ことになる。気づくのは苦情が来てから。
>
> そうならないよう、埋め草のままのUID（全部0・全部F・長さ違い）は**こちらで弾いている**
> （その端末だけの分身が1体できる形に逃がす）。ただし逃がしているだけで、
> その状態では**1枚1体が成立していない**（同じ端末で何枚かざしても同じ子になる）。
>
> **1枚では見抜けない。必ず2枚かざして、別々の子が出ることを確かめること。**

#### 1枚ずつコードを振る方式（併用できる）

QRは紙なので差し替えの仕組みが無く、**1枚ずつ別のコード**が要る。
管理画面の「依代の発行」で作り、一覧の「URL」欄をそのまま使う。
NFCタグでも、手元で1枚ずつ書き込む規模ならこの方式でよい。

| | 共通URL（UIDミラー） | 1枚ずつコード |
|---|---|---|
| 書き込み | 全枚同じ。外注できる | 1枚ずつ違う |
| 在庫（未使用の枚数） | **台帳では分からない** | 分かる |
| 配布元の記録 | 付かない | 付く |
| **限定の姿** | **使えない** | 使える |

**場所限定の姿を使う企画は、QR（または1枚ずつ書き込んだタグ）で行うこと。**

#### よくある間違い

| やってしまうこと | どうなるか |
|---|---|
| **UIDミラーを設定し忘れる** | 全タグが同じURLを返す。1枚1体が成立しない（→ 上の「2枚かざす」） |
| `0` の個数を14個から変える | 長さが合わず弾かれる。UIDは7バイト＝14文字 |
| `/home` を書き込む | かざしても**分身が生まれない**。空の一覧が開くだけ。`/home` は「その端末で既に会った分身の置き場」であって、入口ではない |
| `/summon` を書き込む | `cid` が無いので受け皿に落ちる。`/summon` は `/t` が飛ばす先で、直接書き込むものではない |
| ドメインを付け忘れる | タグを読んでもブラウザが開かない |
| 同じコードを2枚に書く（QR） | 先に読んだ人のものになり、2枚目は同じ子に繋がる |

`/t` と `/q` は**結果がまったく同じ**。違うのは「かざした／読み取った」の記録だけなので、
NFCタグに `/q` を書いても壊れはしない（集計が実態とずれるだけ）。

#### 誰が新しい分身を作れるか（既定は、依代を持つ人だけ）

**依代は売り物（5,500円）なので、その横に「誰でも押せば1体」のボタンは置かない。**
既定では、依代を持たない人の入口（`/add` の3番と `/w`）は閉じている。

| | 作れるか |
|---|---|
| 依代をかざした・読み取った（`/t`・`/q`） | **いつでも作れる。** 設定に関係なく通す |
| その端末で一度でも依代を読んだ人 | 作れる（90日）。2枚目を買った人が締め出されないように |
| 管理者（`/admin` に入っている） | いつでも作れる |
| それ以外 | **作れない。**「依代をお持ちの方だけ」と案内する |

開けたいときは、デプロイに付ける:

```bash
npx wrangler deploy --env="" --var ENTRY_OPEN:1   # 開ける
npx wrangler deploy --env=""                      # 閉じる（既定）
```

#### いま使っているブラウザを「管理者」にする

**そのブラウザで1回この URL を開くだけ。**

```
https://app.waketama.com/admin?key=<合言葉>
```

- 合言葉は Cookie（`waketama_admin`）へ移され、**URLからは消える**（履歴や共有から漏れないように）
- 覚えている長さは **30日**。`Path=/` なので、`/admin` だけでなく `/add` にも効く
- 合言葉は `ADMIN_PASSCODE`。設定されているかは `/api/health` の `admin` で分かる
  （`disabled` と出たら `npm run admin:passcode`）
- **apex（waketama.com）で開いても本体へ転送される**ので、どちらでもよい
- 判定しているのは1箇所だけ: `src/admin.ts` の `isAdminRequest()`

降りるとき:

| やりたいこと | やり方 | 効く範囲 |
|---|---|---|
| **この端末だけ**降りる | 管理画面の右上「この端末を管理者から外す」（`/admin?logout=1`） | その端末だけ |
| 端末を無くした・貸した先を切る | `npm run admin:passcode` で合言葉を変える | **全部の端末が落ちる** |

> Cookieの中身は**合言葉そのもの**。だから、人に貸す端末では必ず降りること。
> 合言葉を平文でやり取りしない（一度でも平文の履歴に出たら、その場で変える）。

> **これは鍵ではなく、扉。** 「依代から来た」の判定はCookieなので、
> curl なら偽れる。防ぎたいのは「画面にボタンがあるから押される」であって、
> 本気の相手ではない。機械的な量産は、回線ごとの1日あたりの上限で止めている。

**1日に作れる数は、通り方で変えてある**（同じ回線から／UTCで数えるので**日本時間の朝9時に戻る**）。

| 通り方 | 1日の上限 |
|---|---|
| 管理者 | **なし。** 試作の読み取り確認で1日に何体も作るので、ここで詰まらせない |
| 依代を持っている | 10体 |
| `ENTRY_OPEN` で誰でも入れる状態 | 3体 |

> 「まだ1体も作っていないのに上限と言われる」ときは、**`/w` を開いた回数**と
> **ミラーの効いていないタグをかざした回数**を思い出すこと。
> どちらも画面上は「ボタンを押していない」が、中では1体作っている。
> 管理者として開いていれば、この数え方からは外れる。

#### 依代を使わず、Webだけで始める

```
https://app.waketama.com/w
```

**`ENTRY_OPEN:1` を立てているあいだだけ動く。** タグが刷り上がる前の時期はこれを立てて、
売り始めたら外す。閉じているときに開かれると、`/add` の案内へ送る（黙って何も起きない、にはしない）。
リンクを配る・QRに刷る・SNSに貼る、どれでもよい。開いた瞬間に1体生まれ、
同じ端末で2回目に開くと同じ子に戻る（開くたびに増えたりしない）。

- **依代に紐づかない。** 端末を変えると引き継ぎコードだけが頼りになる
- **同じ回線から1日10体まで**（依代を持っている人の場合。管理者は上限なし）
- 集計では `web` として数える。`direct`（`/add` のボタンを自分で押した人）とは分けてあるので、
  **配ったリンクがどれだけ効いたかが分かる**
- 台帳には載らない。配布元も限定の姿も付かない

`/add` は同じことを**画面から**行う入口（3番のボタン）。人に教えるときは `/w` のほうが短い。

| やりたいこと | 使うURL |
|---|---|
| キーホルダーを売る | `/t?u=00000000000000`（全枚共通） |
| 場所限定の企画をやる | `/q/<コード>`（1枚ずつ発行） |
| **タグ無しで、いますぐ始める** | **`/w`**（`ENTRY_OPEN:1` が要る） |
| 自分の端末でもう1体作る | `/add`（依代を持つ人か管理者だけ） |

### 5-1. NFCタグ

**外注する（ふつうはこちら）**

1. §5-0 の共通URLと発注内容を、そのままタグ屋さんに渡す
2. 納品されたら、**必ず2枚かざして別々の子が出ることを確かめる**
3. 発注枚数を控えておく（台帳には載らないため。在庫は「概況」の増え方と突き合わせる）

**手元で1枚ずつ書き込む（少量のとき）**

1. 管理画面「依代（タグ・QR）」→ 数・配り方「NFCタグ」・発行の単位を入れて**発行**
2. 一覧の **URL をそのままタグに書き込む**（`https://<ドメイン>/t/<コード>`）
   - 書き込みは手元のNFCアプリで行う。ここでは台帳に載せるだけ
   - **書き込んだら必ず1枚試す。** 書き込みアプリの設定ミスは、配ってからでは直せない
3. 「一覧をCSVで書き出す」で作業記録を残す

### 5-1-2. 「依代を何個持ってもいい」

**端末あたりの上限は無い。** 依代を3つ持てば3体育つ。それぞれ別の分身で、
性格も記憶も混ざらない。一覧（`/home`）に並ぶのは**その端末で開いたことのある分身だけ**なので、
別の端末で育てた子は出てこない（アカウントが無いため）。

混同されやすいが、「1つにつき1体」は**依代の話**であって、人の話ではない。

### 5-2. 場所に置くQR

1. 先に**配布元**を作る（名前は利用者に見せる。設置メモは運営用で見せない）
2. 配り方「QR」・配布元を選んで発行
3. 一覧の「QR」ボタンで画像を出し、PNGで保存して印刷に回す
4. **1枚1コード。** 壁に1枚貼るのではなく、カードやシールとして1人1枚配る

### 5-2-2. 「その場所でしか手に入らない」の作り方

やり方は2つある。**まず1を試すこと。**

**1. そのコードを、その場所にしか置かない（既定）**

姿は150種類（25種族×6色）から等確率。希少なのは**場所**で、手に入れた子には「どこで会ったか」が残る。
仕掛けが要らず、失敗しても取り返しがつく。多くの場合はこれで足りる。

**2. その配布元だけ、出る姿の範囲を絞る（限定の姿）**

管理画面「配布元」→「ここでしか出ない姿にする」。種族だけ／色だけ／両方を選べる。
たとえば「この神社のQRからは**きらつぶ**しか出ない」。

| できること | できないこと |
|---|---|
| 引く**範囲**を狭める | **どの子が出るか**を決めること |
| 種族だけ・色だけを絞る | 既に生まれた分身の姿を変えること |

抽選そのものには運営も手を出せない作りにしてある（`init()` に渡せるのは候補の集合まで）。
**「引き当てた」を「配られた」にしないための線がここ。**

守ること:

- **1種類だけ選ばない。** そこは「その姿しか居ない場所」になり、引く楽しみが消える。
  種族だけ絞って色は残す、くらいが扱いやすい
- **配り始めたあとに変えない。** 先に手に入れた人と後の人で出るものが変わる。
  変えたいなら、新しい配布元を作って別のコードを配る
- 止めるときは**停止中にする**（`active=false`）。止めた配布元の限定は効かなくなり、
  配り残しのコードから読み取られても、ふつうの150種類から引かれる
- **`/add`（依代なし）には限定を出さない。** 場所へ行った意味が消える

利用者の画面には「ここでしか出会えない姿です」とだけ出る。
**何が出るかは、引く前には出していない**（先に見えると、引く意味が無くなる）。

### 5-3. メタバースのエリアを用意する・開放する・まとめる

キャラクター画面の「🌐 メタバース」から、利用者が自分の分身を連れて入る3Dの空間。
エリアは**管理画面でだけ**作る（利用者は作れない）。手順と置ける物の詳細は [METAVERSE.md](METAVERSE.md) §2。

- 場所・時間帯・最初の視点と、置く物（看板＝広告・お知らせ／動画／いまいる子の紹介／歩いて遊ぶミニゲーム3種／
  📱センサー・ARのミニゲーム20種）を決めて保存
- **新しいエリアの開放**: 「準備中」で作る → 「開く」で確かめる（管理者だけ入れる）→ 「公開」＋開放日時で保存。
  それまでは一覧に「近日開放」と出て、日時になると自動で入れる。告知はこの日時に合わせる
- **エリアをまとめる**（例: ひろばと夜空の丘を1つに）: 「エリアをまとめる」でまとめ先とまとめる元を選ぶ。
  置き場所が足りずに外れた物が表示されるので、残したい物を置き直してから保存。
  まとめた元の古いリンク・QRで来た人も、まとめ先へ入れる（配ったQRを刷り直さなくてよい）
- **最初からあるエリア**（ひろば・夜空の丘・和風のエリア・海の底・ゆうえんちなど22か所）も「直す」で変えられる。「元に戻す」で最初の状態に戻る
- 置く物に「お店」を選ぶと、「通貨・お店」で作ったお店をエリアに置ける（ひろば・夏祭り・おかしの国・ゆうえんちに最初から置いてある）
- **保存した瞬間に、部屋にいる人の画面も変わる。** 営業中の部屋を直すときは、変える内容をよく確かめてから
- **広告は「広告として出す」に必ずチェックする**（「広告」の札が付く。外して出すのはステルスマーケティング規制に触れる）
- イベントの会場にするなら「一覧に出す」を外し、`/meta?room=<id>` のリンク（またはQR）を配る
- ミニゲームのクリアの言葉にクーポン案内を入れられるが、**点数はサーバーに残らない**。残るのは通貨のための「その日どの屋台をクリアしたか」だけで、
  「誰が何点だったか」は分からない前提で企画する（クーポンは画面を見せてもらう運用にする）
- 看板に画像を使うと、タップした人は画像を拡大して細かい文字まで読める。**チラシの画像をそのまま載せてもよい**が、文字が小さすぎないか実機で確かめる
- センサーのミニゲームは、置く前に「ミニゲーム管理」の「試す」で、**iPhone と Android の実機で1回ずつ**遊ぶ。
  iPhone は「動きと向き」の許可、マイク・カメラは許可のダイアログが出る。断っても画面の操作で遊べる
- 「ARでおでかけ」の本物のARは Android の Chrome など WebXR 対応端末だけ。iPhone ではカメラの映像の上で遊ぶ形になる。
  イベントの案内に「ARで遊べます」と書くときは、この違いを書き添える

### 5-3-2. NPC（運営の分身）を置く

1. 「NPC・運営の分身」で分身を作る（管理者は上限なし）→「この端末で育てる」で会話して性格を育てる
2. 「NPCとして置く」→ エリア・位置・役目・ひとこと（・リンク）を決めて保存。いまエリアにいる人の画面にもすぐ出る
3. 育てたら「すべて最新の性格にする」（6時間ごとにも自動で取り直す）
- NPC に置けるのは運営の分身だけ。利用者の分身は置けない
- 広告として置く NPC は「広告として出す」に必ずチェック（名前に【広告】が付く）

### 5-3-3. 依代を持たない人に始めてもらう

- **招待リンク**: 「招待・申し込み」で本数・回数・期限を決めて作り、配る（メール・SNS・QRに刷る）。使い切り・期限切れは自動で止まる
- **Web申し込み**: 「申し込みを受け付ける」をオン → `/apply` を告知 → 届いた申し込みを承認。イベント期間などは「すぐリンクを出す」も使える
- **育てた分身を渡す**: 運営の分身から「引き渡し」の招待リンクを作って渡す（1回だけ。渡すと運営の一覧から外れる）

### 5-3-4. 提携店を迎える（通貨をリアルで使えるようにする）

詳しくは [METAVERSE.md](METAVERSE.md) §2-8。

1. 提携店と、**特典の中身・1か月の枚数・有効日数・精算の方法**を決める（特典は景品表示法の上限に収まるように）
2. 管理画面「通貨・お店」→「提携店を足す」→ **表示された暗証番号（8けた）を、その場で安全に伝える**（二度と表示されない）
3. 「商品を足す」で種類「リアル引換券」、提携店・有効日数・1体1か月の数・「店頭での使い方」を入れる
4. 「お店」で「わけたま引き換え所」（またはその提携店専用のお店）に並べる
5. 初めてなら「提携店の引換券への引き換えを受け付ける」をオンにする
6. **自分の分身で1枚引き換え、提携店の端末で `/redeem` を開いて「使ったにする」まで一緒に通す**（QRを読むと番号が入る）
7. 月末に「引換券」で使用済みの枚数を出して精算する（§3）

- 提携をやめるときは、提携店を「停止中」にする（その店の引換券は並ばなくなる。発行済みの券は期限まで使える）
- 店頭の確認画面には、お客さまの名前や分身の情報は出ない。提携店に「誰が使ったか」を聞かれても、こちらも持っていない

### 5-3-5. Web申し込み・招待リンクの告知

- `/lp` の最初のボタンは `/apply`（Web申し込み）。**受け付けを止めているときに告知すると、申し込みページで「受け付けていません」と出る**ので、
  告知の前に「招待・申し込み」で「申し込みを受け付ける」をオンにしておく
- 承認制のときは、申し込みを放っておかない（§1 の赤い数字）。イベント期間などは「すぐリンクを出す」（1回線1日3件まで）

### 5-4. 配ったあとにやってはいけないこと

- **配布元を削除しない。** 止めたいだけなら「停止中」にする
- **同じコードを2か所に置かない。** 先に読んだ人だけのものになる

## 6. 障害のときの切り分け

> ここは運用担当者向けの一次切り分け。実機のブラウザに出ているエラーをPCから直接見て
> コードを追う必要があるとき（開発者向け）は [DEVICE_DEBUG.md](DEVICE_DEBUG.md) を見てください。

### 6-1. 「かざしても何も起きない」

| 確認 | やり方 |
|---|---|
| URLが正しいか | タグを読む端末のブラウザでURLを直接開く。`/summon` に飛べば正常 |
| サービスが動いているか | `/api/health` |
| 端末側の問題か | 別の端末でかざす |

**「かざすたびに同じ子が出る（2枚目なのに1枚目と同じ）」なら、UIDミラーを疑う。**
Workers Logs で `yorishiro.uid_filler` を検索すると、埋め草のまま読み取られた回数が出る。
出ていれば、タグの書き込み設定が足りていない（§5-0）。

`/api/health` で `vectorize` だけ落ちているなら、**会話はできるが思い出せない**状態。
記憶に関わる部分だけが効かないので、その旨を案内しつつ復旧を待つ。

### 6-2. 「会話がおかしい／返事が来ない」

1. `/api/health` の `chat` を見る（使っているモデルが出る）
2. Workers Logs でエラーを見る（会話の本文は記録していない。出るのはエラーの種類だけ）
3. モデル側の障害なら、`CHAT_MODEL` を差し替えてデプロイすれば逃げられる

### 6-3. Service Worker が壊れた

端末側の古いSWが動き続けて、こちらが直しても直らない状態になる。唯一の逃げ道:

```bash
npx wrangler deploy --env="" --var SW_KILL:1
```

`/sw.js` が解除用のスクリプトに差し替わり、端末から抜ける。

「SWが入らない（オフライン案内が出ない）」ときは、先にCSPを疑う。応答ヘッダの
`content-security-policy` に `worker-src 'self'` が無いと、ブラウザは sw.js の登録を拒否する（§6-4）。

### 6-4. 「2回目に開いたら画面が動かない」「ボタンを押しても何も起きない」

1回目は動くのに、開き直すと動かない——なら、CSPの nonce の食い違いを疑う。

| 確認 | 正常 |
|---|---|
| そのページの応答に `ETag` / `Last-Modified` が付いていないか | **付いていない**（付いていたら 304 が返り、古い本文に新しい nonce が重なる） |
| 応答のステータス | 毎回 `200`（`304` なら上と同じ原因） |
| `cache-control` | `no-cache`（管理画面と404は `no-store`） |
| ブラウザのコンソール | `Refused to execute inline script` が出ていない |

`curl -sI https://app.waketama.com/home` で上の3つは見られる。
直し方は `src/index.ts` の `serveAsset`（条件付きリクエストを渡さない・検証子を外す）。
2026-09-23 に一度起きて直した。**ヘッダやアセットの配り方を変えたら、実ブラウザで同じページを2回開くこと。**

### 6-5. 「メタバースに入れない」

[METAVERSE.md](METAVERSE.md) §7 の表を見る。**画面には、入れなかった理由ごとの文言と直し方が出る**ので、
まず利用者に画面の文言を聞く（以前は、どの理由でも「この端末の分身だと確かめられませんでした」だった）。

- 「持ち主だと確かめられませんでした」「持ち主の印が、この端末にありません」→ その端末に持ち主の印が無い・古い。§4-1（引き継ぎコード）で戻す
- 「はじめる前の同意が済んでいません」→ 「キャラクター画面を開く」から同意してもらう
- `waketama.com/meta` を開いている → 自動で `app.waketama.com/meta` に移る。移らないならデプロイ漏れ
- 「このエリアはまだ開いていません／準備中です」→ 管理画面で状態と開放日時を確かめる
- お店・財布・コインのこと → §4-10
- 真っ黒な画面・「この端末では表示できません」→ ブラウザの WebGL が切れている（省電力設定・古い端末）

### 6-6. 管理画面に入れない

`ADMIN_PASSCODE` が未設定だと開かない（設定漏れが情報公開になるのを防ぐため）。

```bash
npm run admin:passcode   # プロンプトに合言葉を入力する
npm run secrets:list     # ADMIN_PASSCODE が並べば設定済み
```

`npx wrangler secret put <合言葉>` と打つと、**その文字列を名前にしたシークレット**ができるだけで、
管理画面は開かないままになる。よくある間違い。

## 7. 変更を出すとき

```bash
npm run typecheck        # 型
npm test                 # 単体・結合（workerd上で動く）
npm run test:e2e         # 実画面（ローカルの dev に対して）
npx wrangler deploy --env="" --dry-run   # 積み荷の確認
```

全部通ってから:

```bash
npm run db:migrate:remote   # マイグレーションがあるときだけ。**デプロイより先**（最新は 0015_meta_economy.sql）
npm run deploy
```

マイグレーションを後に回すと、新しいコードが無いテーブルを読んで落ちる。順番を守ること
（0015 を当て忘れると、メタバースのお店・財布だけが「開けませんでした」になる）。

**同意の文面の版（`CONSENT_VERSION`）を上げた変更を出すと、全員が次に開いたとき1回だけ同意の画面に戻る。**
告知が要るほどの変更か（使い道が増えた等）を、出す前に決めておく。2026-09-24 に版5へ上げた（法人への提供を入口の同意に束ねた）。

デプロイ後は `/api/health` の `version` が新しいコミットになっているかを見る。
実機では、応答ヘッダ `x-waketama-version` でも確認できる。

**CSP・キャッシュ・Service Worker に触れた変更のあとは、実ブラウザで次を確かめる**
（テストは通るのに本番で黙って壊れる種類。2026-09-23 に3つまとめて見つかった）:

- 同じページを**2回**開いて、2回目も動く（§6-4）
- コンソールに `Refused to ...`（CSPの拒否）が出ていない
- `/home` を開いたあと、ブラウザの開発者ツールで Service Worker が登録されている
- 視線入力（`/eyes`）で、MediaPipe の読み込みが拒否されていない

## 8. やってはいけないこと（理由つき）

| やらないこと | 理由 |
|---|---|
| 会話の中身をログに出す | 「運営は読まない」という約束の根拠が消える |
| 運営側から分身を削除する | 取り違えたときに戻せない |
| 持ち主トークンを買い手に渡す | 名前の変更も削除もできてしまう。渡すのは引換券 |
| `CharacterState.init()` に**個体**を指定する口を足す | 「引き当てた」が「配られた」に変わり、集める体験が壊れる。渡してよいのは**引く範囲**（`BirthPool`）までで、その中から引くのは常に乱数 |
| 配り始めた配布元の「限定の姿」を後から変える | 先に手に入れた人と後の人で出るものが変わる。新しい配布元を作ること |
| `localStorage` のキー名（`sodatsukake_*`）を変える | 既存の利用者全員が、自分の分身の持ち主でなくなる |
| `[assets].not_found_handling` を変える | アセット層が先に応答して `/api/*` が全部死ぬ（過去に起きた） |
| 引換券を無期限で発行する | 失効させ忘れが必ず起きる |
| 本人の同意なく、実在の人物を模した分身を作る・売る | いったん通すと後から戻せない |
| 買い手に渡す経路で `buildCard`（本人向け）を使う | 会話の抜粋・覚え書き・年収まで渡る（過去に起きた）。買い手向けは必ず `buildBuyerCard` |
| 同意に束ねる使い道を増やす・減らすのに `CONSENT_VERSION` を上げない | 過去の同意を、書いていなかった使い道に流用することになる（2026-09-24 に「法人へ渡すことを許可する」を束ねたときは版5へ上げた） |
| 入口の同意の画面から、束ねた使い道の説明を省く・畳む | 見せずに束ねたら同意にならない。「法人へ渡すこと」は特に、渡るもの・渡らないものを全部見せる |
| 持ち主が許可を外した分身の券を、出し直す・期限を延ばす | 取り消しを運営が上書きすることになる（仕組みでも 409 で止まる） |
| HTMLに `ETag` を付けたまま返す・304 を返す | nonce が食い違って、2回目以降の訪問で全ページのスクリプトが止まる |
| MCPの回数を、持ち主の会話と同じ入れ物で数える | 買い手が使い切ると、持ち主本人がその日話せなくなる |
| メタバースで、利用者が部屋を作れる口・自由な文字を送れる口を足す | 見知らぬ人（子どもを含む）に任意の画像・文字を見せられる。挨拶は決まった台詞、スタンプは決まった種類だけにしてある |
| 広告の看板を「広告として出す」を外して置く | ステルスマーケティングになる。札は外せない作りにしてある |
| `wrangler.toml` の Durable Object マイグレーション（`v1`・`v2`）のタグを変える・消す | 既存の分身（CharacterState）やメタバースの部屋が作り直され、データが消える |
| 通貨をお金で売る・換金する・利用者どうしで送れる口を足す | 前払式支払手段（提携店で使えるなら第三者型の登録が要る）・資金移動・RMT の問題になる。やるなら実装の前に専門家に相談 |
| 提携店の暗証番号を平文で残す・メールで送る | 他人が店頭の代わりに「使った」にできてしまう。なくしたら作り直す |
| 運営が店頭の代わりに引換券を「使った」にする・使用済みの券を戻す | 二重に使える穴になる。取り消せるのは未使用の券だけ（返金つき） |
