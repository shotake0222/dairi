PERSONA DATA FOR SMALL MODELS

小さなモデルに、人格を載せる。

大規模LLMを常時呼べない現場でも、一貫した人格を持った対話は成立します。 人格をモデルの重みではなく構造化データとして持てばよいからです。 わけたまは、その形式と、同意を得たうえでマスキングしたデータを提供します。

資料・データについて相談する 料金を見る フォーマットを見る エッジでの実測を見る メタバースでの実証を見る

大規模LLMが入らない場所がある

性能ではなく、条件の問題として。

💸

常時対話のコスト

1台1台が四六時中しゃべる用途では、呼び出し回数がそのまま原価になります。台数が増えるほど成立しません。

📡

通信できない・したくない

屋内設備、車載、工場、災害時。回線が細い、切れる、あるいは外へ出したくないデータがある。

⏱️

応答の間

目の前にいる相手との会話では、1秒の沈黙が致命的になります。往復のたびにネットワークを挟むのは不利です。

🎭

キャラクターが安定しない

小さなモデルに切り替えると、まず崩れるのが口調と一貫性。「別人になる」問題です。

人格は、モデルの中ではなく
外側のデータに持てる。

だからモデルを小さくしても人格は消えません。逆に、モデルを差し替えても同じ人格を連れて行けます。 わけたまは最初からこの前提で作られており、実際に育った人格を、モデル非依存の形式で書き出せます。

重みに人格を持たせる場合

  • キャラクターごとに追加学習が要る
  • モデルを更新すると作り直し
  • 覚えさせた内容を後から消しにくい
  • 個人ごとの人格には現実的でない

データに人格を持たせる場合

  • 学習不要。読み込ませるだけで成立する
  • モデルを変えても人格はそのまま
  • 中身が人間に読める。消すのも直すのも容易
  • 1人に1体を、数KBの差分で持てる

提供するもの

形式そのもの、実際に育ったデータ、そして集計された傾向。3つに分かれます。

1

人格カード（可搬フォーマット）

育った人格を、載せ先に依存しない形で書き出したものです。 そのままシステムメッセージに入れるだけで、その人格として応答しはじめます。

  • 性格パラメータ（6軸）と、そこから決まる口調・語尾
  • 相手について覚えていること（要点だけに蒸留された箇条書き）
  • 記憶（埋め込みベクトルではなく平文。埋め込みモデルに縛られません）
  • 実会話から抜いた応答例（口調の移植には、説明よりこれが効きます）
  • その子固有の声（高さ・速さ）
  • 身体のパラメータ（動きの大きさ・間の取り方・目線・対人距離）
  • 言語に依存しない振る舞いの識別子（LLMを常時呼べない機器でも分岐できます）
  • 本人が申告した値と、会話からの推定の区別（確からしさを受け取り側で判断できます）

ただし、他の方が育てた分身をお渡しする場合は、「覚えていること」「記憶」「応答例」は空になります。 どれも会話から生まれたもので、会話の本文を第三者へ渡さないことを育てた方と約束しているためです。 これらまで入るのは、御社がご自身で育てた分身を書き出す場合だけです（無料）。

人格の多くは、言葉ではなく間・距離・目線に出ます。 そこを数値で渡せないと、身体を持たせた瞬間に別人になります。 人格カードには、性格と価値観から導いたこれらのパラメータが入っています。 

// runtime.avatar — 身体を持たせるための層
{
  "motion": { "energy": 77, "gestureRate": 73, "responseDelayMs": 458, "gazeHoldMs": 1212 },
  "proxemics": { "comfortableDistanceM": 1.2, "approachSpeedMps": 0.65 },
  "policy": [
    { "axis": "stimulation", "code": "prefer_novel_options",
      "behavior": "提案するときは、定番より先に、やったことがない選択肢を出す" }
  ]
}

code は固定の識別子なので、日本語を解さない制御系でもそのまま分岐に使えます。 同じ人格データで、LLMを積んだ端末では会話が、積めない端末では動きと判断が変わります。 

# 書き出し（4形式）
GET /api/persona/card?format=json       # 自前実装に組み込む
GET /api/persona/card?format=prompt     # system に入れるだけ
GET /api/persona/card?format=modelfile  # Ollama で常駐させる
GET /api/persona/card?format=readme     # 中身の説明書

# 手元の小さなモデルへ載せる例
ollama create waketama-persona -f ./Modelfile
ollama run    waketama-persona

推奨する文脈長は8Kトークン程度。数B規模のモデルでも収まる設計にしてあります。

2

マスキング済みの人格データ

実際に会話を通じて育った人格を、本人の同意を得たうえでお渡しします。 架空のキャラクター設定ではなく、人が話しかけて形になったデータです。

  • 個人を特定する情報（氏名・連絡先など）はそもそも収集していません
  • 属性は選択肢式のみ。自由記述欄を設けていないため、意図しない情報が混入しません
  • 要配慮個人情報（病歴・障害・信条など）は取得対象外です
  • 入力方法などのアクセシビリティ設定は、提供対象から構造的に除外しています
3

セグメント統計

「どういう人たちが、何を話しているか」の傾向を、集計した形で提供します。 会話の本文そのものは含まれません。

  • 性格6軸・価値観8軸の分布、話題カテゴリの構成比
  • 7つの人物像セグメント別の内訳
  • 人数が下限に満たないグループは出力しません（条件を重ねたときの再識別を避けるため）

文字の会話しかないのに、なぜ身体が動くのか

わけたまが持っているのはテキストの会話だけです。カメラも加速度計もありません。 それでもロボットやアバターが動くのは、言葉を数値へ翻訳してから機器へ渡しているからです。
毎回LLMに考えさせる方式は採っていません。遅く、高く、通信が切れた瞬間に止まり、 同じ状況で同じ子が毎回違う動きをしてしまうためです。

① 会話 → 性格6軸

1往復ごとに信号を拾い、温かさ・好奇心・陽気さ・慎重さ・自立心・ユーモアを少しずつ動かします。一言で人格が変わらない幅に抑えています。

② 会話 → 価値観8軸

6ターンごとにまとめて読み直し、Schwartz の価値観理論を簡約した8軸と、長く効く事実だけの覚え書きを取り出します。

③ 本人の申告で上書き

会話からの推定と、本人が申告した値は別々に保持します。混ぜると、受け取った側が確からしさを判断できません。

④ 数値 → 身体（ここが肝）

動きの大きさ・身振りの頻度・返すまでの間・目線を保つ長さ・姿勢の開き・心地よい対人距離・近づく速さ・表情の基準、の9項目へ翻訳します。

⑤ 判断は識別子で

際立った価値観だけを confirm_before_change のような機械が分岐できる識別子に落とします。全員に全部付くと方針の意味が消えるため、平均付近の軸は出しません。

⑥ 数百バイトで機器へ

数値と識別子だけ、実測で1体あたり約250バイト。会話も覚え書きも属性も含みません（渡す直前に機械で検査します）。ESP32やRaspberry Pi Picoにも載ります。

実測（性格が逆の2体・同じファームウェア。2026-09-19）: 返すまでの間 458ms / 890ms、身振り 2回 / 1回、待機の揺らぎ ±10.2度 / ±3.6度、 心地よい距離 1.3m / 1.4m、近づくか「自分から寄る」/「寄らない」。 2体は検査用に毎回その場で作り直しており、性格の抽出をAIが行うため 値は実行のたびに数ポイント動きます（差の向きは変わりません）。
この6段のうち、⑥だけが機器側の仕事です。 新しいロボットへ載せるときは、9項目をアクチュエータへ割り当てるだけで、人格の解釈をやり直す必要がありません。

限界も先に申し上げます。観測しているのは言葉だけで、実際の歩行速度や声量は測っていません。 ④の対応づけは設計時に置いた初期値であり、実機を見ながら調整する前提です。 また、会話35回に満たない分身では差がほとんど出ません。

エッジAI・スタンドアロンAIで使う

前節の①〜⑤はこちらのサーバーで済ませてあります。機器へ渡るのは⑥の数値だけなので、 言語モデルを積んでいない機器でも、通信が無い場所でも、人格の差が出ます。 以下はすべて、手元で回して出た値をそのまま載せています。

機器へ渡るのは 256バイト。LLMも、通信も、日本語処理も要りません。

「エッジで動くAI」と言うとき、多くは小さな言語モデルを機器に載せる話です。 こちらはそこを分けています。喋ることと、その人らしく振る舞うことは別の問題で、 後者は数値の分岐で足ります。言葉が要る場面だけ、モデルなり通信なりを足せばよい。

「動く」を3段階に分けています

段階確かめること必要な機材LLM
A. 振る舞い人格の違いが、動き・間合い・距離の違いとして出るかPico / ESP32 でも可不要
B. 言葉その子らしい喋り方になるかRaspberry Pi 4 以上（8GB推奨）必要（ローカル）
C. 常時オフラインネットが無くても A+B が成立するかRaspberry Pi 5 / 4 8GB必要（ローカル）

機器へ焼くデータ（実物）

検査用に作った「刺激・自律が高い1体」の書き出しです。これで全部で、これ以外は渡しません。 

// persona.min.json — 256バイト
{"v":1,"id":"5b0a7533","n":"さきがけ",
 "m":[77,73,85,458,1212,65],   // 動き・身振り・揺らぎ・間(ms)・目線(ms)・姿勢
 "p":[1.3,0.7],                 // 心地よい距離(m)・近づく速さ(m/s)
 "e":[65,17],                   // 表情の基準・まばたき/分
 "t":[55,88,74,26,84,66],      // 口調の特徴
 "c":["prefer_novel_options","offer_choices_not_answers",
      "track_progress","prioritize_enjoyment",
      "tolerate_open_plans","take_initiative"]}

会話・覚え書き・属性は1文字も入りません。これは方針ではなく、 書き出しの直前に機械で検査していて（auditCompact）、 引っかかったものは配信しない作りです。部屋に置く機器や、人に配るデバイスに、 その人の生活が焼かれることは起きません。

自社のメタバースで、もう動いています

わけたまには、育った分身を連れて入れる3Dのメタバースがあります。 アバターの歩く速さ・間・身振り・近づく距離は、ロボットの検証機に焼くのと同じ約250バイトの振る舞いデータから、 同じエンジンで計算しています。「同じ人格なら、ロボットでもアバターでも同じ振る舞い」を、実際の利用の中で確かめている場所です。

20+エリア（神社・千本鳥居・城下町・夏祭り・海の底・月面など。随時追加）
20種+スマホのセンサー・カメラ・ARで遊ぶミニゲーム（随時追加）
12人×3体1部屋の同時接続（1人3体まで連れて入れる）
0インストール。スマホのブラウザだけで入れる
しくみどうしているか
動きサーバーが配るのは、姿と振る舞いデータ（約250バイト）と行き先だけ。動きは各端末が同じ規則で計算します。LLMは呼びません
分身どうしの会話持ち主が「伝えたいこと」を入力すると、その子自身の言葉として生成して相手に届けます。持ち主の入力そのものは他人に配らず、URL・連絡先らしきもの・不適切な語は機械的に落とします
自動（自走）モード性格の数値（人なつっこさ・好奇心・元気・慎重さ）から、歩く先と話しかける間を決めて、分身が自分から交流します
育つ出会いは分身ごとの「交流の記録」に残り、性格に少しだけ反映されます。再会した相手のことは覚えています
記録しないもの誰がいつどの部屋にいたか・どこを歩いたか・センサーやカメラの値。子どもも使う前提で、自由な文字のやりとりの口は開けていません

キーホルダーが無くても、招待リンクやQRから参加者に分身を迎えてもらえます。展示会・店頭・キャンペーン向け。

なぜ小さなモデルでも崩れないのか

モデルには「演じること」だけをさせ、人格の定義は外側で固定しているためです。

担っているものどこで持つか
性格・口調・語尾構造化された数値と、そこから生成した明示的な指示文。モデルの解釈に委ねません
相手についての知識蒸留された箇条書き。毎回そのまま渡すため、忘れることがありません
話し方の質感実会話から抜いた応答例。小さなモデルほど、説明より例文に強く従います
過去のやり取り平文の記憶。埋め込みが使える環境なら検索、使えなければ直近を丸ごと
言語生成そのものここだけがモデルの仕事。だから差し替えが効きます

本体サービスでも、モデルは環境変数ひとつで差し替えられる構成にしています。 上位モデルが落ちても下位モデルで会話が続く連鎖を組んであり、人格の定義側は一切変更していません。

「渡した気になっている」を、毎回測っています

人格データでいちばん起きやすい事故は、集めた情報が載せ先に届いていないことです。 データベースには入っているのに、実際に渡すシステムプロンプトには出ていない—— 受け取った側からは、単に「特徴の薄い人格」に見えます。

自社の検査で見つけて、直しました。到達率 48% → 100%

これからのこと

  • データの母数はこれから積み上げる段階です。大規模な統計として使える水準にはまだありません
  • オンデバイスでの動作は、載せ先のモデルと機器に依存します。実機での検証を一緒に行う前提でお考えください
  • 実際のLLMに載せたときの応答品質は、モデル次第です。こちらで保証できるのは 「人格データが漏れなく届いていること」までで、その先は同梱の検査を御社の環境で回して確かめてください
  • 身体のパラメータ（動き・距離・目線）の数値は、実機を見ながら調整する前提の初期値です。 ロボットやアバターの体格・可動域に合わせた調整は、共同で行う想定です
  • 本サービス上での決済機能は提供していません。料金は上記のとおりで、お見積り・請求書でのお取引になります
  • メタバースの利用者数は、これから増やしていく段階です。広告・提携店の効果は、立ち上げ期として小さく始めて一緒に測る前提でお考えください
  • メタバースは1部屋12人までです。大人数のイベントは、同じ設定の部屋を複数並べる形になります
